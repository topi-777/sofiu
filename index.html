Introducción

El video explica qué es Supabase, una plataforma en la nube que funciona como alternativa a Firebase y que entrega una base de datos PostgreSQL, autenticación de usuarios y una API lista para usar, todo desde el navegador.

Durante el video se crea un proyecto, se arma una tabla de productos (products) con datos como laptop, monitor y mouse, y se muestra cómo Supabase genera una REST API automática. Después se prueba con Postman (leer, insertar, actualizar y borrar) y se termina con lo más importante: proteger los datos con RLS (Row Level Security), políticas y usuarios autenticados con tokens JWT.

Conceptos Fundamentales

1. Supabase

Plataforma en la nube que ofrece un backend completo (base de datos, usuarios, archivos y funciones) sin tener que programar ni mantener un servidor propio.

2. PostgreSQL

Base de datos relacional que guarda la información en tablas con filas y columnas. Es el "motor" que usa Supabase por dentro.

3. REST API automática

Direcciones web que Supabase crea solas para cada tabla (con PostgREST), para leer, agregar, modificar o borrar datos con peticiones GET, POST, PATCH y DELETE.

4. API Key

Clave que se envía en las cabeceras (apikey y Authorization) para identificar a la aplicación que consulta la API. La clave pública (anon) no debe considerarse un secreto, por eso hace falta RLS.

5. RLS (Row Level Security)

Seguridad a nivel de fila: reglas (políticas) que deciden qué usuarios pueden ver, insertar, actualizar o borrar cada fila de una tabla.

Cuestionario Resuelto

1. ¿Cuál es el tema principal del video? Explica de qué trata.

El tema principal es Supabase y cómo usarlo como backend. El video muestra desde cero cómo crear un proyecto, armar una tabla, obtener una API automática, probarla con Postman y protegerla con RLS y usuarios autenticados.

2. ¿Qué problema o necesidad tecnológica se aborda?

Crear un backend desde cero (servidor, base de datos, usuarios y API) lleva mucho tiempo. Supabase lo resuelve en minutos. Además, se aborda un problema de seguridad: si la API es pública, cualquier persona con la clave podría leer o modificar los datos, por eso se necesitan reglas de acceso.

3. ¿Cuáles son los cinco conceptos más importantes? Define cada uno.

  1. Supabase: backend en la nube con base de datos, auth y API.
  2. PostgreSQL: base de datos relacional organizada en tablas.
  3. REST API: enlaces automáticos para leer y escribir datos con peticiones web.
  4. API key / JWT: la clave identifica a la app; el token JWT identifica al usuario que inició sesión.
  5. RLS y políticas: reglas que filtran qué filas puede ver o cambiar cada usuario.

4. ¿Qué herramientas, programas o tecnologías se mencionan y para qué sirven?

  • Supabase: plataforma donde se crea el proyecto y la base de datos.
  • GitHub: se usa para iniciar sesión en Supabase.
  • PostgreSQL: guarda los datos en tablas.
  • PostgREST: genera la API REST a partir de las tablas.
  • Postman: programa para probar las peticiones a la API.
  • JWT (jwt.io): sitio para ver cómo se decodifica un token de sesión.
  • JavaScript (supabase-js): biblioteca para usar Supabase desde una página web.

5. ¿Qué procedimientos o pasos se explican? Preséntalos en orden.

  1. Entrar a Supabase e iniciar sesión con GitHub.
  2. Crear un proyecto nuevo (nombre, contraseña de la base de datos, región y plan gratuito).
  3. Crear la tabla products con columnas id, created_at y name.
  4. Cargar filas de ejemplo (laptop, monitor, mouse).
  5. Abrir la documentación de la API (API Docs) y copiar la URL y la clave.
  6. Probar la API en Postman con las cabeceras apikey y Authorization.
  7. Activar RLS y crear políticas (por ejemplo, lectura para todos).
  8. Agregar la columna user_id y crear políticas para insertar, actualizar y borrar solo lo propio.
  9. Probar con un usuario autenticado y su token JWT.

6. ¿Qué ejemplos prácticos aparecen? Explica uno detalladamente.

Aparece la tabla products, las peticiones en Postman (GET, POST, PATCH y DELETE) y las políticas de RLS. Ejemplo detallado: primero se consulta la tabla sin seguridad y la API devuelve los productos. Luego se activa RLS sin crear ninguna política y la misma consulta devuelve una lista vacía, porque nadie tiene permiso. Después se crea una política de lectura y los datos vuelven a aparecer. Así se ve cómo las políticas controlan el acceso. (Ver las imágenes en Recursos visuales).

7. ¿Qué conocimientos previos son necesarios para comprender lo explicado?

Hay que saber qué es una base de datos con tablas, filas y columnas; tener nociones de cómo funcionan las peticiones web (GET, POST, JSON); y conocer algo de JavaScript y de herramientas como el navegador y Postman. También ayuda saber qué es un usuario autenticado.

8. ¿Qué ventajas o beneficios ofrece la tecnología o procedimiento?

Ahorra tiempo porque no hay que programar el servidor; la API se crea sola y se actualiza cuando cambian las tablas; usa PostgreSQL, que es una base de datos potente; trae autenticación de usuarios incorporada; y tiene un plan gratuito muy útil para aprender y hacer prácticas.

9. ¿Qué dificultades, errores o precauciones deben considerarse?

Si se deja la tabla sin RLS, cualquiera con la clave pública puede acceder a los datos. Si se activa RLS y no se crea ninguna política, la API devuelve una lista vacía y parece que "no funciona". También hay que tener cuidado de no exponer claves privadas (como la service role) y de escribir bien las políticas para que cada usuario solo toque sus propias filas.

10. ¿Cómo aplicarías lo aprendido en un proyecto informático real?

Lo aplicaría en un sistema de inventario o de gestión (por ejemplo, para un taller, un comercio o un sistema escolar). Crearía las tablas en Supabase, conectaría mi página web con JavaScript y activaría RLS para que cada usuario solo vea y modifique la información que le corresponde.

11. ¿Qué parte del video consideras más importante y por qué?

La parte de seguridad con RLS y políticas. Crear la API es fácil, pero lo importante es que los datos estén protegidos. Que una página funcione no significa que sea segura: hay que controlar quién puede leer, insertar, modificar o borrar.

12. ¿Qué conocimientos nuevos adquiriste y cómo los explicarías a otra persona?

Aprendí que una base de datos en la nube puede generar su propia API y que la seguridad se configura con reglas por fila. Se lo explicaría así: "Supabase es como un armario con cajones (tablas). La API es la puerta para pedir cosas, y RLS es el guardia que decide quién puede abrir cada cajón".

Aplicación Práctica (Código JS)

Lo aprendido se puede usar para mostrar en una página web la lista de productos guardados en Supabase. Procedimiento:

  1. Crear el proyecto y la tabla products.
  2. Activar RLS y crear la política de lectura.
  3. Copiar la URL del proyecto y la clave pública (anon).
  4. Consultar los datos desde JavaScript.

Ejemplo corto de código con fetch (los valores entre < > se reemplazan por los del proyecto):

const URL = "https://<tu-proyecto>.supabase.co/rest/v1/products";
const KEY = "<tu-clave-anon>";

async function cargarProductos() {
  const respuesta = await fetch(URL + "?select=*", {
    headers: {
      apikey: KEY,
      Authorization: "Bearer " + KEY
    }
  });
  const productos = await respuesta.json();
  console.log(productos); // [{ id: 1, name: "laptop" }, ...]
}

cargarProductos();

Si RLS está activo y no existe una política de lectura, productos será una lista vacía [].
